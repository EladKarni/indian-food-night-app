Architecture review

indian-food-night-app · 2026-05-26

The codebase has already been split fine — small components, many hooks, a query layer. The friction now is the opposite of monoliths: scatter. The same domain logic is re-implemented behind several shallow modules, and the deepest concept in the app — money math — has no single seam to test through.

After — one deep module, callers read totals

deep module

Problem

Five callers each re-derive subtotal/tax/total their own way; one drops tax entirely, two pick different constants.

Solution

One module that takes orders + intent (host-collect, guest-share, group) and returns the figures. Callers stop doing arithmetic.

Wins

  • Locality: every money bug lives in one module
  • The interface is the test surface
  • Leverage: one rule, 5 call sites
  • Tax/no-tax discrepancy becomes impossible
  • TAX_RATE vs TAX_MULTIPLIER drift gone
  • Deletion test: complexity concentrates, not moves

4 · Resolve OrderList's dual-mode interface

src/components/OrderList.tsx:41–43 · all call sites pass flags, none pass orders

Before — props OR hook, decided at runtime

orders = propOrders ?? ordersHook.orders
loading = propLoading ?? ordersHook.loading
error = propError ?? ordersHook.error

Caller must know which half is live. The orders / loading / error props are part of the interface but unused everywhere.

Plus 6 hooks + filter + group + sum + edit state in one 139-line module.

After — one source of orders

OrderList (view)

takes orders + view flags

useOrders (one owner of data)

Drop the unused props, or commit to props-only. One mode.

Problem

The interface advertises an injectable-orders mode no caller uses; the module silently falls back to its own hook.

Solution

Remove the dead props (the seam isn't real — one adapter, not two), or make orders a required prop and lift the hook to the pages.

Wins

  • Interface shrinks to what's used
  • One adapter ≠ a seam — stop pretending
  • Testable: feed orders, assert render
  • No ambiguity about data source

Top recommendation

Start with #1 — collapse the totals math.

It's the deepest concept in the app (Venmo collection, host totals, guest shares) and the most scattered: five orchestrations, two constants, and one path that silently drops tax — all untested. A single computeBill module gives the codebase its first real test surface and removes a whole class of money bugs. Candidates #2 and #3 then have something solid to lean on.
